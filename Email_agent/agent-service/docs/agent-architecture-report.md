# MailFlow Agent-Service — Complete File-by-File Technical Report

> Generated by reading every source file under `Email_agent/agent-service/src/`.
> Scope: this report documents ONLY the agent service (`agent-service/src/`) — the AI orchestration layer that sits in front of the MailFlow backend via MCP.

---

## 1. High-Level Architecture

The agent-service is an **Express + LangGraph** backend that powers a conversational AI assistant for email-marketing campaign management. A user message flows through a compiled **LangGraph state machine** (21 nodes) that:

1. Loads session memory → detects intent → (optionally) builds a multi-step plan
2. Routes to a **domain agent** (Campaign / Analytics / Inbox / Enrichment / Research / Bulk)
3. Validates the chosen tool/args → checks if the action is **risky** (needs approval)
4. Executes the MCP tool against `mailflow-mcp-server` (which talks to the MailFlow backend)
5. Formats a final response (with optional OpenAI "humanizing" pass) → saves memory

Two LLM providers are integrated (`OpenAIService` is primary/active, `GeminiService` is legacy/unused), used **only** for: intent classification, multi-step plan detection, response humanization, reply summarization, and AI campaign-draft generation. **Email personalization/outreach content itself is 100% template + heuristic driven (no LLM calls)** — see section 7.

```
HTTP request
  → middleware (requestId, auth, rate-limit)
  → controllers/agent.controller.ts (chat / confirm / cancel)
  → graph/workflow/agent.workflow.ts  (compiled LangGraph)
       loadMemory → detectIntent → [resumeWorkflow | planDetection]
         planDetection → [executePlanStep | manager]
           manager → {campaign|analytics|inbox|enrichment|research|bulk}
             → validation → {clarification | approval | formatResponse}
               approval → {executeTool → phase3Continuation} → formatResponse
       → saveMemory → END
  → response formatted via lib/agentResponseFormatter.ts
```

## 2. Entry Point & Infrastructure Layer

### `app.ts`
Builds and exports the Express app (doesn't start the server). Middleware order: trust proxy → helmet (security headers, CSP off since it's a JSON API) → CORS (`buildCorsOptions` supports deny-all / allow-all / explicit allow-list) → body parsers (size limit from `env.BODY_SIZE_LIMIT`, default 100kb) → request logger → three tiered rate limiters (global, `/api/agent/chat` ≈20/min, `/api/agent/confirm` ≈10/min — `/health` excluded) → routes → 404 handler → global error handler.

### `index.ts`
Process entrypoint. Imports `env` first (fail fast on bad config), calls `initStores()` to create Redis-backed session/pending-action stores (silently falls back to in-memory if Redis unavailable), starts the HTTP server with carefully tuned timeouts:
- `keepAliveTimeout = 65s` (just above AWS ALB's 60s idle timeout, prevents 502s)
- `headersTimeout = 66s` (must exceed keepAliveTimeout to dodge a Node/proxy race)

Implements **graceful shutdown**: tracks open sockets in a `Set`, on SIGTERM/SIGINT calls `server.close()`, drops `keepAliveTimeout` to 1ms to drain fast, force-destroys remaining sockets after `SHUTDOWN_TIMEOUT_MS` (10s), disconnects Redis, exits 0/1. Also registers `unhandledRejection`/`uncaughtException` safety nets.

### `config/constants.ts`
Static constants: `SERVICE_NAME`, `SERVICE_VERSION`, `REQUEST_ID_HEADER`, `DEFAULT_APPROVAL_TTL_MS` (10 min), `SESSION_TTL_SECS` (24h), `DEFAULT_LLM_MODEL`/`MAX_TOKENS`/`TEMPERATURE`, `DEFAULT_MCP_TOOL_TIMEOUT_MS` (30s), server shutdown/keep-alive timeouts.

### `config/env.ts` 
Zod-validated environment config (`env`), exits process on invalid config (except in tests). Validates: `JWT_SECRET`/`MCP_SERVICE_SECRET` (≥32 chars), optional LLM API keys, CORS mode (deny/allow-all/allow-list), body size limit (regex on byte units), rate-limit overrides, log level/pretty flag, optional `REDIS_URL` (graceful in-memory fallback).

### `config/intents.ts`
The **intent taxonomy** — 90 intents total. Exports `Intent` (compile-safe union), `ALL_INTENTS` tuple, `INTENT_DOMAIN` map (campaign/analytics/inbox/settings/general/enrichment/research/bulk), and `INTENT_RULES` — a keyword-pattern scoring system (`pattern` substring + `weight` 0.1–1.0) used for deterministic intent detection. `INTENT_CONFIDENCE_THRESHOLD = 0.06`, `FALLBACK_CONFIDENCE = 0.1`. Special intents: `out_of_domain` (LLM-only, no keyword rules) and `upload_csv` (triggered by file presence, not text).

### `middleware/auth.ts`
`requireAuth` — verifies `Authorization: Bearer <jwt>`, resolves user identity from `sub`→`userId`→`id` claims (never from request body), attaches `req.authContext = { userId, email, rawToken }`. Maps `TokenExpiredError`→401 `AUTH_EXPIRED_TOKEN`, `JsonWebTokenError`→401 `AUTH_INVALID_TOKEN`. Token is never logged; `rawToken` kept only for forwarding to MCP within the same request.

### `middleware/errorHandler.ts`
Global error handler (registered last). Three categories in order: (1) malformed JSON body → 400 generic message, (2) `AppError` (operational, 4xx/5xx — strips `details` from 5xx in production), (3) unknown errors → 500 generic "unexpected error" (stack traces logged, never returned).

### `middleware/notFound.ts` / `requestLogger.ts`
`notFound` — standardized 404 for unmatched routes. `requestLogger` — assigns `requestId` (from `X-Request-ID` → `X-Correlation-ID` → fresh UUID), echoes it back in response header, logs request arrival and completion (method, path, status, duration, userId, sessionId) — never logs auth headers.

### `routes/` (agent.routes.ts, health.routes.ts, index.ts)
- `agentRouter`: 3 POST routes — `/chat` (with multer memory-storage upload, 10MB limit, CSV/XLSX only), `/confirm`, `/cancel`.
- `healthRouter`: `GET /health` (liveness) and `GET /health/ready` (readiness), unauthenticated.
- `index.ts` composes: `/health` → no auth, `/api/agent` → `requireAuth` → `agentRouter`.

### `controllers/agent.controller.ts`
Thin HTTP layer, 3 handlers:
- **`chat`**: validates `message` (1–4000 chars) + optional `sessionId` (Zod), generates sessionId if absent, base64-encodes uploaded file into `pendingCsvFile`, invokes `agentGraph.invoke()`, returns either `formatApprovalRequired()` or `formatChatSuccess()`.
- **`confirm`**: validates `pendingActionId`/`actionId`, atomically transitions the pending action via `pendingActionService.confirm()`, then either resumes a multi-step plan (`planExecutionService.resumePlan()`) or executes a single step (`toolExecutionService.executeFromState()`). **Detects business-logic failures** (`{ success: false, error: { code, message } }` without `isToolError`, e.g. `MAILFLOW_CONFLICT`) and routes to `formatWorkflowError()` — *this is the exact code path fixed for "Issue 2" in a previous session* (lines ~298-310).
- **`cancel`**: validates and calls `pendingActionService.cancel()`.
- Helper `describeConfirmStepResult()` produces human-readable one-line tool-result descriptions (never raw JSON); `formatPlanConfirmSuccess()` summarizes multi-step results.

### `controllers/health.controller.ts`
`getLiveness` returns status/service/version/uptime/timestamp. `getReadiness` currently returns `{status: "ok", checks: {process: "ok"}}` (Phase 1 — future phases will probe MCP/LLM connectivity).

### `types/`
- `common.ts`: branded primitive types (`UserId`, `SessionId`, `RequestId`) preventing accidental mixing of semantically-different strings; `AuthContext` interface.
- `express.d.ts`: augments `Express.Request` with `requestId` and optional `authContext`.
- `mcp.ts`: `McpToolCall`, `McpToolResult` (`{ data, isToolError, rawContent }`), `McpCallOptions`.
- `tools.ts`: `KNOWN_TOOL_NAMES` (42 MCP tools), `KnownToolName`, `isKnownTool()` guard, and a typed input interface for every tool grouped by domain (campaign, analytics, inbox, settings, personalization, CSV/recipients, enrichment, Phase 2 company-search, Phase 3 intelligence, bulk workflow), unified in `ToolInputMap`.

## 3. The LangGraph Workflow (Core Reasoning Pipeline)

### `graph/state/agentGraph.state.ts`
Defines `AgentGraphState` (LangGraph `Annotation.Root`) — the single state object threaded through every node. Every field has an explicit reducer (mostly "last-writer-wins"; `messages` uses `messagesStateReducer`). Field groups: conversation, session/auth (incl. `rawToken`, redacted from logs), intent/confidence/`llmExtractedArgs`, routing (`agentDomain`), tool execution (`toolName`/`toolArgs`/`toolResult`), approval (`requiresApproval`/`pendingActionId`), response (`finalResponse`/`formattedResponse`/`error`), campaign wizard & selection state, multi-step planning (`plan`/`planIndex`/`planResults`), CSV ingestion, **bulk workflow state machine** (`bulkWorkflow` — 13-step `BulkWorkflowStep`), AI campaign wizard, enrichment flow, **Phase 3 company-intelligence chaining** state, and **workflow concurrency primitives** (`activeWorkflowLock`, `workflowStack` — suspend/resume mechanism, e.g. when Phase 3 interrupts an in-progress enrichment).

### `graph/workflow/agent.workflow.ts`
Compiles the graph (`agentGraph`). **21 nodes**, with conditional-edge routing functions:
- `routeFromDetectIntent`: `resume_workflow` → `resumeWorkflow`; else → `planDetection`
- `routeFromPlanDetection`: `plan.length >= 2` → `executePlanStep`; else → `manager`
- `routeToAgent` (in manager.node): `agentDomain` → one of 6 domain nodes or `formatResponse`
- `routeFromValidation`: `formattedResponse` set → `formatResponse`; no `toolName` → `clarification`; else → `approval`
- `routeFromApproval`: `requiresApproval` → `formatResponse`; else → `executeTool`
- `routeAfterPhase3Continuation`: `pendingPhase3ContinueExecute` → loop to `executeTool`; else → `formatResponse`

Full edge topology:
```
START → loadMemory → detectIntent → [resumeWorkflow | planDetection]
  resumeWorkflow → formatResponse → saveMemory → END
  planDetection → [executePlanStep | manager]
    executePlanStep → formatResponse → saveMemory → END
    manager → {campaign|analytics|inbox|enrichment|research|bulk|formatResponse}
      <domain> → validation → {clarification|approval|formatResponse}
        clarification → saveMemory → END   (no tool execution)
        approval → {executeTool|formatResponse}
          executeTool → phase3Continuation → {executeTool(loop)|formatResponse}
      formatResponse → saveMemory → END
```

### Node-by-node summary

| Node | Role |
|---|---|
| **`loadMemory`** | First node. Restores last 10 messages, active campaign, sender defaults, all wizard/enrichment/bulk/Phase-3 state from session store. Checks `sessionSchemaVersion` for forward-compat (clears volatile state if snapshot is newer). Lazily expires workflow locks/stack items/deadlines and emits a one-shot `workflowExpiredNotice`. |
| **`detectIntent`** | Highest-priority deterministic overrides (manual bulk-row detection, bulk reset, active-bulk-workflow reply mapping, `resume_workflow` phrase, CSV-upload bypass, Phase-3-during-enrichment interruption with workflow-stack suspend, enrichment context replies, `extract_domain` pre-check) — only then falls through to **LLM-first detection** (`intentDetectionService.detectWithLLM`, never throws, has deterministic fallback). Also extracts inline recipient emails via regex into `extractedRecipients` (consumed later to auto-inject `add_recipients`). |
| **`resumeWorkflow`** | Pops most recent suspended workflow off `workflowStack`, restores its full snapshot, recreates a workflow lock, builds a context-aware "resume" prompt. |
| **`planDetection`** | Decides single-step vs multi-step (2-3 tool calls). Bypasses planning for CSV uploads, active enrichment wizards, Phase-3 intents, research intents, and bulk intents (these need deterministic chaining the generic planner can't reconstruct). Delegates to `plannerService.detectPlan()`. |
| **`manager`** | Routes `intent` → `agentDomain`, with **workflow-state priority** overriding plain intent-based routing (active bulk workflow → `bulk`; active enrichment → `enrichment`; campaign draft/selection/AI-wizard/active-campaign-context → `campaign`, etc.). Implements a **concurrency guard**: blocks switching workflows if a non-interruptible `activeWorkflowLock` is active (except `resume_workflow`/`discard_enrichment`). Cleans up stale cross-domain state on switch. |
| **`campaign` / `analytics` / `inbox` / `enrichment` / `research` / `bulk`** | Thin wrappers delegating to the corresponding domain agent (`agents/*.ts`) — see section 4. |
| **`validation`** | Safety gate after every domain agent: `formattedResponse` set → go straight to `formatResponse`; no `toolName` → `clarification`; tool chosen → `approval`. Defensive check: blocks `update_campaign` from reaching MCP without a `campaignId` (audit-logs `AI_TOOL_BLOCKED`). |
| **`clarification`** | Builds structured JSON responses (`status`: `draft_ready` / `collecting_input` / `needs_input` / `redirect`) when params are missing or the campaign wizard needs to show a draft/step. `update_smtp` is redirected to the Settings UI rather than collected in chat. Routes straight to `saveMemory` (no tool call). |
| **`approval`** | Determines if the chosen action is risky (`start_campaign`, `resume_campaign`, `update_smtp` — via `ApprovalPolicyService`). If risky, creates a `PendingAction` (10-min TTL) and sets `requiresApproval=true`; otherwise passes through. |
| **`executeTool`** | Runs the MCP tool for safe (non-approval) actions via `toolExecutionService.executeFromState()`. Auto-injects `add_recipients` after a successful `create_campaign` if the user supplied inline emails (returns a 2-step `planResults` so the response renders a mini-summary). |
| **`executePlanStep`** | Executes a multi-step plan in one node invocation: runs all safe steps in sequence, pauses (creates `PendingAction` with full `planContext`) at the first risky step, resolves runtime `campaignId` for later steps after `create_campaign`, and auto-injects `add_recipients`. |
| **`phase3Continuation`** | Deterministically chains Phase-3 intelligence tools after `fetch_website_content` succeeds (`extract_company_profile` → `classify_industry` → `detect_pain_points` → `generate_outreach_draft`/`score_lead`), building each subsequent tool's args from accumulated `pendingPhase3Scratch`. Loops back to `executeTool` via `pendingPhase3ContinueExecute`; no LLM calls — pure deterministic chaining. Caps website content at 8000 chars. |
| **`formatResponse`** (`finalResponse.node.ts`, ~2365 lines — the largest node) | Two-phase: (1) deterministic `buildResponse` always produces a well-formed reply (priority order: workflow-expired notice → pre-formatted response → error → approval-required → out-of-domain → general-help → contextual help → no-tool-selected → multi-step plan summary → tool-result-specific formatters e.g. `formatStatsMessage`, `formatRepliesMessage`, `formatSmtpMessage`, `humanizeToolError`, `formatCampaignList`, etc.); (2) optional **OpenAI enhancement** (`maybeEnhanceWithOpenAI`) for data-dense intents (`get_campaign_stats`, `list_replies`) — rewrites the deterministic text into more natural prose, silently falls back to phase-1 output on any failure. |
| **`saveMemory`** | Last node — persists the turn (messages, intent, domain, campaign id/draft, enrichment/bulk/Phase-3 state, tool-call record) to the session store via `sessionMemoryService.saveTurn()`. Has substantial side-effect logic: captures `senderDefaults` after `create_campaign`, handles `SMTP_SELECTION_REQUIRED` recovery, saves campaign-selection lists, advances enrichment step after CSV parse, clears state on enrichment completion, recomputes workflow-deadline/lock. Memory errors are caught and logged but never crash the graph. |

## 4. Agents Layer (`agents/`)

`BaseAgent` is an abstract class — every domain agent extends it, exposes a `domain` string and an async `handle(state)` returning a state patch. Agents **only decide which MCP tool + args to use**; they never call MCP directly, never make approval decisions, never format final text.

- **`AnalyticsAgent`** — simplest agent. Single tool (`get_campaign_stats`); resolves `campaignId` from `llmExtractedArgs` → `activeCampaignId`; if neither present, triggers a campaign-selection flow via `get_all_campaigns` + `pendingCampaignAction`.

- **`CampaignAgent`** — by far the largest/most complex agent (handles 19 intents). Owns three multi-turn wizards: (1) step-by-step **campaign creation** (collects name → subject → fromName → fromEmail → body, or AI-assisted draft via OpenAI), (2) **update_campaign** (select field → provide value), (3) **CSV upload** (parse → preview → confirm/discard → save). Also drives an **8-step AI campaign wizard** and **SMTP profile selection**. Uses regex-based deterministic extraction (`tryExtractFromMessage`, `parseExplicitCampaignId`, scheduling-text parsers `extractSchedulingText`/`extractDurationText`/`parseDurationMinutes`) to pull fields straight from natural language when possible. Marks `start_campaign`/`resume_campaign` as requiring approval. Note: scheduling currently returns a JSON preview only — **no backend persistence yet**.

- **`EnrichmentAgent`** — orchestrates the contact-enrichment pipeline (CSV → batch enrich → preview → confirm/customize/discard → save to campaign) AND the **Phase 1-3 intelligence tools** (validate email, fetch website, search/verify company, analyze company, detect pain points, generate outreach, full enrich). Implements **workflow concurrency**: when the user interrupts an active enrichment with a Phase-3 request ("analyze this company"), it snapshots the enrichment state onto `workflowStack`, takes a lock, runs Phase 3, and the user can later say "resume" to pick the enrichment back up. Heavy use of the deep-intelligence libs from section 7 (`buildDeepCompanyProfile`, `generateCompanyPainPoints`, `buildExecutiveIntelligence`, etc.).

- **`InboxAgent`** — pure dispatcher. Static `TOOL_MAP` of 11 inbox/reply intents → MCP tools (`list_replies`, `summarize_replies`, `show_hot_leads`, `draft_reply_suggestion`, `get_reply_intelligence_summary`, `get_autonomous_recommendation`, `preview_sequence_adaptation`, etc.), resolved via `resolveToolArgs`.

- **`ResearchOutreachAgent`** — **read-only**, never sets `toolName`/`toolArgs`/calls MCP. Takes 1-10 company URLs from the message, runs the full deep-intelligence pipeline (website fetch → profile → pain points → personas → triggers → executive intelligence → strategic narrative → email sequence → external business intel) and returns a markdown report directly as `formattedResponse`. Two output modes: "executive intelligence" (deep strategic analysis) vs "template-first outreach" (copy-ready email drafts). Always explicitly states no campaign/recipients/sends were triggered.

## 5. Services Layer (`services/`)

- **`intentDetection.service.ts`** — Three modes: `detect()` (sync, deterministic keyword scoring against `INTENT_RULES`, threshold 0.06, falls back to `general_help`), `detectWithLLM()` (async, **the active path** — calls `openai.classifyIntent`, validates with `LLMIntentResponseSchema`, accepts if confidence ≥ 0.7, else falls back to deterministic), `detectAsync()` (legacy deterministic-first). Includes a **research-intent override**: 2+ URLs in the message + research phrasing forces a research intent regardless of LLM output.

- **`planner.service.ts`** — `detectPlan()` decides if a message needs 2-3 sequential tool calls. Excludes wizard continuations, CSV uploads, response-only intents, campaign-action intents (CampaignAgent owns those), and cases where OpenAI isn't configured. Calls `openai.planSteps()`, validates with `LLMPlanResponseSchema`, resolves each step's args via `resolveToolArgs`, tags `requiresApproval` via `ApprovalPolicyService`.

- **`planExecution.service.ts`** — `resumePlan()` is invoked from the `/confirm` endpoint when a paused plan is confirmed. Re-executes from `pausedStepIndex` onward via `toolExecutionService.executeFromState()`, stops on first error.

- **`toolExecution.service.ts`** — The graph→MCP adapter (`executeFromState`). Validates tool name + auth, builds `AuthContext`, **pre-resolves the SMTP profile for `create_campaign`** (avoids a backend edge case where `Number(undefined ?? 0)` produces `smtpSettingsId: 0`), dispatches via `McpClientService`, returns `{ toolResult }` or `{ error }`. Re-throws auth-category errors (`AUTH_*`) so they propagate to the HTTP layer; everything else becomes a recoverable state error.

- **`mcpClient.service.ts`** — Typed wrapper exposing named methods (`createCampaign`, `getCampaignStats`, `listReplies`, etc.) plus a generic `dispatch(toolName, args, auth)` for runtime tool selection (validates against `isKnownTool`). Delegates everything to `mcpToolCaller`.

- **`mcpToolCaller.ts`** — Lowest-level invocation. Opens a **per-call** MCP session (`openMcpSession`), enforces a 30s timeout via `Promise.race`, retries transient errors up to 3× with exponential backoff (120/240/480ms), normalizes MCP content blocks into `{ data, isToolError, rawContent }`, maps everything to typed `McpError`.

- **`approvalPolicy.service.ts`** — Tiny static policy: `requiresApproval(intent)` / `approvalReason(intent)`. Currently `start_campaign` and `resume_campaign` are flagged risky with human-readable reasons ("This will send emails... and cannot be undone"). (Note: `update_smtp` is gated at the prompt/system-prompt level too — see section 8.)

- **`pendingAction.service.ts`** — Manages the full `PendingAction` lifecycle (`pending` → `confirmed` → `executed`, or `cancelled`/`expired`). `create()` generates a UUID + TTL-based `expiresAt`; `validate()` enforces ownership/status/expiry (throws `APPROVAL_NOT_FOUND`/`ForbiddenError`/`APPROVAL_EXPIRED`/`ConflictError`); `confirm()` **atomically** transitions pending→confirmed *before* execution to prevent double-execution on retried requests. Backed by `IPendingActionStore` — either `InMemoryPendingActionStore` or the Redis-backed store, chosen by `createPendingActionStore()` factory.

- **`redisPendingAction.store.ts`** — Redis implementation: `SET ... EX <ttl>` on create, `SET ... EXAT` to preserve original TTL on update, `DEL` to remove. All errors caught/logged, never propagated (best-effort persistence).

- **`sessionMemory.service.ts`** — Typed read/update helpers over the session store. Bounds `messages` to `MEMORY_MAX_MESSAGES` (20) and `recentToolCalls` to `MEMORY_MAX_TOOL_CALLS` (10). `saveTurn()` is the convenience wrapper called by `saveMemory` node.

- **`auditLog.service.ts`** — Fire-and-forget structured audit trail (`AuditLogService`, backed by a separate Pino `auditLogger`). Events cover the full lifecycle: `chatReceived`, `intentDetected`, `agentSelected`, `toolAttempt`/`toolSuccess`/`toolFailure`, `approvalRequired`, `pendingActionCreated`/`Executed`, plus **security events** `confirmDuplicate`/`confirmExpired`/`confirmForbidden`. Never logs secrets; errors swallowed.

- **`gemini.service.ts`** — **Legacy/unused** Google Generative AI integration (intent classification, reply summarization, response enhancement, plan steps via Gemini 1.5 Flash with `responseSchema`-controlled generation). Kept as a fallback reference; OpenAI is the active provider.

- **`openai.service.ts`** — **The active LLM provider** (model: `gpt-4o-mini`, JSON mode via `response_format`). Methods: `classifyIntent` (returns `{intent, confidence, arguments?}` JSON, with an extensive prompt including 7 few-shot examples and explicit extraction rules for `campaignId`/`limit`/`query`/`filters`), `planSteps` (multi-step plan JSON, max 3 steps), `enhanceResponse` (rewrites deterministic text to natural prose, preserving all facts), `summarizeReplies`, `summarizeWebsiteContent` (strict `SUMMARY` + `FOCUS AREAS` format, ≤60 words, no invented facts), and `generateCampaignDraft` (auto-generates `{name, subject, fromName, fromEmail, body}`, merging user-known fields with priority).

## 6. Core Library Utilities (`lib/`)

- **`agentResponseFormatter.ts`** — The single place that shapes every API response. `parseAgentResponse()` safely normalizes the raw `finalResponse` string (JSON-with-status / JSON-without-status / plain text / empty) into a discriminated `AgentResult`. Exports `formatChatSuccess`, `formatApprovalRequired`, `formatConfirmSuccess` (uses `buildConfirmMessage` — per-intent friendly labels e.g. "Campaign started successfully."), `formatCancelled`, `formatWorkflowError` (`{ response, error: true }` — *the path used for MAILFLOW_CONFLICT and other business-logic failures*).

- **`apiResponse.ts`** — `sendSuccess`/`sendFailure` envelope helpers (`{success, data/error, requestId}`), used by every controller and the global error handler.

- **`autonomousDecisionEngine.ts`** — Heuristic engine (`decideNextBestAction`) that recommends one of 13 SDR actions (continue/pause/stop sequence, escalate to human, change tone/CTA, mark meeting-ready, prioritize lead, etc.) based on lead-engagement signals, with a strict priority order (stop conditions → meeting intent → objections → deliverability risk → engagement scoring → fallback). `coordinateAutonomousAgents()` then routes the decision to the owning agent (`reply_intelligence`/`sdr_strategy`/`analytics`). All confidence scores and reasoning strings are deterministic/explainable — no ML model.

- **`errors.ts`** — Typed `AppError` hierarchy (`AuthError`, `ForbiddenError`, `ValidationError`, `NotFoundError`, `ConflictError`, `ApprovalRequiredError` (HTTP 202), `McpError`) with a 16-value `ErrorCode` enum. The global error handler distinguishes these (operational, safe to surface) from unknown programming errors (masked).

- **`logger.ts`** — Pino structured logger factory (`createLogger(component)`) with automatic redaction of `password`, `token`, `rawToken`, `authorization`, `secret`, `apiKey`, `smtp.password`, `toolArgs.*`, etc. Separate `auditLogger` child instance for the audit trail.

- **`mcpClient.ts`** — `openMcpSession(rawToken)` creates a fresh per-call SSE client+transport, injecting `X-Service-Token` (service secret) and `X-Forwarded-Authorization: Bearer <userJwt>` on both the SSE GET and POST messages. `session.close()` is best-effort (errors swallowed).

- **`mcpErrorMapping.ts`** — `WORKFLOW_PENDING_TTL_MS` (30 min) + `computeWorkflowDeadlineIso`/`isWorkflowDeadlineExpired`. `isTransientMcpOrNetworkError()` (drives retry logic — checks for ECONNREFUSED/timeout/5xx-style errors). `toUserSafeMcpMessage()` + `classifyTransportMessage()` convert raw transport errors into safe, sanitized user messages (strips URLs/hostnames/IPs).

- **`parseManualBulkRows.ts`** — Parses freeform pasted recipient lists ("Acme Corp, https://acme.com, john@acme.com") into structured `BulkRow[]` via regex extraction (email, website, company name), with `normalizeWebsite`/`isValidEmail` validation and markdown-link/bullet stripping.

- **`planTypes.ts`** — Type contracts for multi-step planning: `PlannedStep`, `PlanStepResult`, `PlanResumptionContext` (the structure stored inside a paused `PendingAction` so a confirmed plan can resume mid-flight). `MAX_PLAN_STEPS = 3`.

- **`redisClient.ts`** — Lazy Redis singleton (`getRedisClient`). Returns `undefined` if `REDIS_URL` unset or connection fails — every caller must handle the in-memory-fallback case. `lazyConnect: true`, `maxRetriesPerRequest: 3`. Masks the password in logs.

- **`sdrStrategy.ts`** — Pure heuristic engine selecting the best **CTA**, **tone**, and **sequence type** for a lead based on score/role/company-size/industry/pain-points (`selectBestCTA`/`selectBestTone`/`selectBestSequenceStrategy` → `buildSdrStrategy`). All decisions are rule-based with explicit `reasoning` strings — fully explainable, no ML.

- **`toolArgResolver.ts`** — The central security/sanitization layer before any MCP dispatch. `resolveToolArgs(toolName, {extractedArgs, activeCampaignId})` strips **forbidden keys** (`userid`, `accountid`, `token`, `secret`, `password`, `auth`, etc. — never trust LLM output for identity/auth), validates `campaignId` (must be a positive integer string, rejects `"all"`/`"camp-1"`/`0`/`-1`), and has a per-tool resolver function for each tool family (campaign, recipients, replies, sequence-adaptation scenario inference, SMTP, enrichment pass-through).

- **`websiteInput.ts`** — `isEmailLike`/`normalizeWebsiteUrlOrUndefined`/`isValidWebsiteInput` — rejects email addresses mistaken for URLs, normalizes bare domains and `https://` URLs (strips `www.`, fragments, trailing slashes; requires ≥1 dot in hostname).

- **`workflowConcurrency.ts`** — `createWorkflowLock`, `isLockExpired`, `isStackItemExpired`, `pushWorkflowStack`/`popWorkflowStack` (immutable LIFO stack ops), `buildEnrichmentSnapshot`/`clearEnrichmentUiState` — the primitives behind the suspend/resume mechanism (e.g., Phase-3 interrupting enrichment).

- **`phase3IntentFromMessage.ts`** — Tiny regex-based override (`inferPhase3IntentFromUserMessage`) that forces `analyze_company`/`detect_pain_points`/`generate_outreach`/`enrich_company` when the message explicitly says so, preventing the LLM from misclassifying these as `general_help`.

- **`phase3ToolChains.ts`** — `PHASE3_TOOL_QUEUE`: hardcoded, ordered MCP-tool sequences for each Phase-3 action (e.g. `enrich_company` → `[extract_company_profile, classify_industry, detect_pain_points, score_lead, generate_outreach_draft]`).

## 7. Intelligence / Outreach Personalization Engines (`lib/`, 25 modules)

**Important finding (confirms what was discussed earlier in this project):** all 25 of these modules are **100% rule-based, template-driven, and deterministic** — regex/keyword pattern matching, hardcoded phrase libraries, switch-case industry classification, scoring formulas, and **stable hashing for variation** (same inputs always produce the same output — no randomness, no LLM calls inside these modules). The only LLM usage anywhere in the agent is in `services/openai.service.ts` (intent classification, planning, response humanization) — **not** in email content generation.

Pipeline flow (roughly, as chained by `EnrichmentAgent`/`ResearchOutreachAgent`):

```
fetchWebsiteIntelligence (real HTTP fetch)
  → companyWebsiteEnrichment (keyword-dictionary signal extraction: services, industry, buyer, tech, hiring, finance, sales...)
  → deepCompanyProfile (industry/sub-industry classification via regex + 10 hardcoded "domain hints" for known companies; confidence scoring formula)
  → hiringIntelligence (job-title regex extraction, department classification, hiring-volume buckets)
  → triggerIntelligence (growth/expansion/transformation/AI/partnership/hiring-burst signal detection + urgency scoring formula)
  → companyPainPointEngine (industry switch-case + signal-presence pain-point templates)
  → personaIntelligence / personaNarrativeEngine (cascading regex on hiring depts/triggers/industry → persona selection + persona-specific narrative templates)
  → executiveIntelligenceEngine (executive priorities, strategic triggers, buyer-persona profiles, 8 commercial-opportunity scoring formulas)
  → strategicNarrativeEngine / industryNarrativeMapper (6 hardcoded industry narratives selected via regex; subject-line theme picking via stable hash)
  → executiveSignalInterpreter / triggerAwareOutreach (signal → human-readable interpretation templates)
  → executiveOpeningArchetypes (10 archetype openings, selected via stable hash + industry keyword override)
  → executiveCTAEngine (8 CTA styles mapped from persona via regex)
  → executiveEmailArchetypes (8 full email-body templates with {{placeholders}})
  → executiveOutreachSequence (assembles an 8-email sequence from the archetype templates)
  → humanization chain: outreachHumanizationEngine → executiveConversationalRealism → commercialPsychologyLayer → cadenceHumanizationEngine → microPhraseRealism
       (all regex replacement + stable-hash phrase-variation passes that scrub "AI fingerprints" / robotic phrasing)
  → strategicLanguageVariation (phrase-library substitution via stable hash, prevents repetition across a sequence)
  → externalBusinessIntelligence (optional: fetches /news /press /blog, regex-detects partnership/funding/acquisition/expansion events)
  → outreachIntelligenceEngine / contactEnrichment (lead scoring formulas, basic template generation, batch summaries)
```

Key takeaway for the user: **"template selection" exists conceptually** (10 strategy types referenced in `templateInjectionEngine` / `TEMPLATE_OPTIONS` from the bulk-workflow side, plus 8 executive-archetype templates here), but the actual email *body text* is built by string-template interpolation + heuristic personalization — not by an LLM writing fresh copy per company. Stable hashing ensures variation across recipients without randomness (reproducible/auditable).

## 8. Memory, Prompts, Schemas & MCP Integration Notes

### Session Memory (`memory/`)
- **`sessionMemory.store.ts`** — Defines `ISessionMemoryStore` interface + `SessionSnapshot` type (messages, intents, campaign context, all wizard/enrichment/Phase-3/bulk state, workflow lock/stack, tool-call history, `sessionSchemaVersion`). `InMemorySessionStore` (Map-based, dev/test) and `createSessionStore()` factory that prefers Redis when `REDIS_URL` is configured and reachable.
- **`redisSession.store.ts`** — Production `RedisSessionStore`: `SETEX session:{userId}:{sessionId}` with `SESSION_TTL_SECS` (24h, refreshed on every write), JSON serialization, cursor-based `SCAN` for `clear()`. All errors caught/logged — Redis outage degrades gracefully to a cache-miss, never crashes the workflow.

### Prompts (`prompts/`)
- **`system.prompt.ts`** — Global identity/guardrail prompt: establishes the agent as an MCP-only orchestration layer (4 domains: Campaigns/Analytics/Inbox/Settings), **6 hard constraints** (no direct API access, no guessing, no secret leakage, no fabricated stats, no cross-user access, no unapproved risky actions), the **approval workflow** rules (`start_campaign`/`resume_campaign`/`update_smtp` require explicit confirmation — inform, wait, don't execute), and response-style guidelines (concise, summarize don't dump JSON, ask one question at a time).
- **`analytics.prompt.ts`** — Constrains the LLM to exactly one tool (`get_campaign_stats`, read-only), defines the campaign-ID resolution order, formatting rules (lead with campaign name, compute derived rates only from present data, never fabricate), and explicitly forbids prescriptive advice.
- **`campaign.prompt.ts`** — Lists the 7 allowed campaign tools with a clear approval matrix (start/resume/SMTP-update = yes, others = no), per-tool argument requirements, SMTP password-masking rules (never ask for/reveal passwords), and `activeCampaignId` reuse guidance.
- **`inbox.prompt.ts`** — 2 read-only tools (`list_replies`/`summarize_replies`), strong **PII/privacy guidance** (never log verbatim reply content, no inferences about individuals, surface unsubscribe/complaint signals prominently, no editorial commentary), pagination context injection.

### Schemas (`schemas/`)
- **`llmIntent.schema.ts`** — Zod validation for the LLM's intent-classification JSON: `intent` checked against the 90-value `ALL_INTENTS` whitelist (rejects hallucinated intents), `confidence` clamped to [0,1] and rounded to 4 decimals, `arguments` with typed optional fields (`campaignId`, `recipientEmail` with `.email()`, `scenario`/`mode` enums, `filters` record, plus top-level fallback fields for `create_campaign`).
- **`plan.schema.ts`** — Zod validation for multi-step plans: each step's `tool` checked against `KNOWN_TOOL_NAMES`, `intent` against `ALL_INTENTS`, `description` capped at 200 chars, `steps` array capped at `MAX_PLAN_STEPS` (3) — explicitly to prevent prompt-injection-driven plan bloat.

### `integration/mcp-connection.note.ts`
Documents (and provides) the MCP connectivity contract: SSE transport over HTTP to `MCP_SERVER_URL` (default `localhost:4000/sse`), `getMcpConnectionConfig()` (config snapshot) and `checkMcpConnectivity()` (opens+closes a session, measures latency — used for readiness probes). Documents the **auth header contract** (`X-Service-Token` validated via `crypto.timingSafeEqual`, `X-Forwarded-Authorization` forwarded-but-not-verified by MCP — MailFlow backend is the JWT authority), the full call stack (`executeToolNode → ToolExecutionService → McpClientService → McpToolCallerService → openMcpSession → mcp-server → MailFlow backend`), the **SDK version pin** (1.21.0 — newer versions break FastMCP completion registration), and a troubleshooting guide for common connection errors (500/401/ECONNREFUSED/timeout).

## 9. Summary — What This Agent Actually Does

1. **Conversational orchestration**: every user message goes through intent detection (deterministic keyword rules + LLM classification with Zod-validated structured-arg extraction), then routes to one of 6 domain agents.
2. **Safety-first tool execution**: a strict pipeline (validation → approval gate → MCP dispatch) ensures risky actions (`start_campaign`, `resume_campaign`, `update_smtp`) always pause for explicit user confirmation via the `PendingAction` lifecycle (atomic state transitions prevent double-execution).
3. **Multi-step planning**: simple requests route directly to a domain agent; compound requests (≤3 steps) get an LLM-generated plan that executes safe steps automatically and pauses at the first risky one.
4. **Stateful multi-turn workflows**: campaign-creation wizards, CSV/recipient-enrichment flows, and the **bulk campaign workflow** (rows → template-strategy selection → batch generation → approval → draft → conflict-aware launch) are all modeled as explicit state machines persisted in session memory, with a **suspend/resume mechanism** (`workflowStack`/`activeWorkflowLock`) so e.g. a Phase-3 company-analysis request can interrupt and later resume an in-progress enrichment.
5. **Deep company intelligence & outreach generation**: a 25-module pipeline does real website fetching + keyword/regex-based signal extraction, industry/persona/trigger classification, and assembles personalized cold-email sequences from a large library of hardcoded archetype templates, CTA styles, and phrase-variation engines — all deterministic (stable-hash-seeded), reproducible, and auditable. **No LLM is used to write the email copy itself.**
6. **Resilience & observability**: graceful Redis fallback everywhere, structured Pino logging with automatic secret redaction, a dedicated audit-log trail for security-relevant events, typed error hierarchies mapped to user-safe messages, and careful HTTP-server timeout tuning for ALB compatibility + graceful shutdown.
